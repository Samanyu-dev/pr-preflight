# PR Pre-flight: init

Generate a starter `.preflight.md` at the repo root by actually looking at
the codebase, not by guessing generic defaults.

## 1. Don't clobber existing config

If `.preflight.md` already exists at the repo root and `$ARGUMENTS` doesn't
contain `--force`, print its current contents, say it already exists, and
stop. Don't overwrite someone's hand-tuned rules silently.

## 2. Detect naming convention

For the 1-2 most common source languages in the repo (by file count, via
`git ls-files`), sample function/variable declarations across several files
and determine the dominant naming convention (snake_case, camelCase,
PascalCase). If it's genuinely mixed with no clear majority, say so instead
of forcing a rule.

## 3. Detect test layout

Check whether tests live as sibling `*.test.*`/`*.spec.*` files next to the
source file, or under a separate `test/`/`tests/`/`__tests__/` directory
mirroring the source tree. Note which, so the main command's missing-test
check knows where to look for a sibling.

## 4. Detect paths worth excluding

Using `git ls-files`, find tracked directories that look vendored/generated
(`vendor/`, `third_party/`, `generated/`, `dist/`, `build/`, or similar) —
only ones actually tracked in git, since gitignored paths never show up in a
diff and don't need an exclusion.

## 5. Write the file

Write `.preflight.md` at the repo root with what was actually observed —
not a generic template. Roughly:

```md
# Repo preflight config

Generated by /pr-preflight:init — edit freely, this is a starting point.

- Naming convention in <language>: <observed convention>.
- Tests live in <observed layout>.
- Ignore: <detected paths>, if any were found.
```

Omit any section where nothing conclusive was found rather than filling it
with a guess. Print the final file content so the user can review it before
their next `/pr-preflight:preflight` run.
